# Restoring Backups from `database-backup` Cron Task

This guide explains how to restore PostgreSQL backups generated by the `database-backup` cron task.

## Backup Format

The cron task generates a gzip-compressed SQL dump:

- File pattern: `database-backups_<db-name>-<timestamp>.sql.gz`
- Dump type: **plain SQL**, compressed with gzip (not `pg_dump -Fc` custom format)

Because this is a plain SQL dump, restore with `psql` (or DBeaver "Execute script"), **not** `pg_restore --format=c`.

## Prerequisites

- PostgreSQL client installed locally (`psql`)
- Valid database credentials
- Correct target database name (for Render/managed DBs, this is often **not** `postgres`)

Check `psql`:

```powershell
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" --version
```

## Option 1 (Recommended): Restore with `psql`

### 1) Decompress `.sql.gz` to `.sql`

```powershell
$in  = "C:\path\to\database-backups_xxx.sql.gz"
$out = "C:\path\to\backup.sql"

$input  = [System.IO.File]::OpenRead($in)
$output = [System.IO.File]::Create($out)
$gzip   = New-Object System.IO.Compression.GzipStream($input, [System.IO.Compression.CompressionMode]::Decompress)
$gzip.CopyTo($output)
$gzip.Dispose(); $output.Dispose(); $input.Dispose()
```

### 2) (Optional but recommended) Reset target schema before import

Only run this if you want a fully clean restore:

```powershell
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -h <host> -p <port> -U <user> -d <database> -v ON_ERROR_STOP=1 -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public AUTHORIZATION <user>; GRANT ALL ON SCHEMA public TO <user>;"
```

### 3) Restore the SQL file

```powershell
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -h <host> -p <port> -U <user> -d <database> -v ON_ERROR_STOP=1 -f "C:\path\to\backup.sql" *> "$env:USERPROFILE\Desktop\restore.log"
```

### 4) Verify

```sql
select current_database(), current_user;
select count(*) from pg_tables where schemaname='public';
```

## Option 2: Restore directly from `.sql.gz` (without temp `.sql`)

```powershell
gzip -dc "C:\path\to\database-backups_xxx.sql.gz" | & "C:\Program Files\PostgreSQL\18\bin\psql.exe" -h <host> -p <port> -U <user> -d <database> -v ON_ERROR_STOP=1
```

If `gzip` is not available on Windows, use Option 1.

## DBeaver Workflow (Works)

1. Open the correct connection/database.
2. Ensure Local Client points to PostgreSQL 17/18 (`psql.exe` available).
3. Use `Tools` -> `Execute script` (native script execution).
4. Select `.sql` file and run.

## DBeaver Workflow (Do Not Use for this backup type)

Do **not** use PostgreSQL `Restore` wizard with `Format: Custom` for these files.
That path uses `pg_restore` and will fail with:

- `did not find magic string in file header`

## Troubleshooting

### `psql is not recognized`

Use full path:

```powershell
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" ...
```

### `permission denied for schema public`

You are either:

- connected to the wrong DB (often `postgres` instead of app DB), or
- missing schema privileges

Check:

```sql
select current_database(), current_user;
select has_schema_privilege(current_user, 'public', 'CREATE') as can_create;
```

If needed (with admin account):

```sql
GRANT USAGE, CREATE ON SCHEMA public TO <user>;
```

### `relation "<table>" already exists`

Target DB is not clean. Drop/recreate schema (see reset command above) then restore again.

### Thousands of `relation ... does not exist` errors

This is usually a cascade after an early failure.
Inspect the **first** `ERROR:` in `restore.log`.

```powershell
Get-Content "$env:USERPROFILE\Desktop\restore.log" | Select-String "ERROR:" -Context 3,3 | Select-Object -First 1
```

## Notes

- Cron backups are valid plain SQL dumps; restore failures are usually environment/permissions/target-DB issues.
- Prefer restoring into the application database name from `DATABASE_URL`, not the default `postgres` database.
